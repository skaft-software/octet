- One newly created 3-GiB, 2-vCPU Linux Cua Space, `pi-proof-v010-rc-20261104`, is used sequentially. Each side has a fresh isolated HOME and its own loopback-only scripted/mock model provider. Real Pi 1.4.0 runs on the left and candidate octet on the right; two independent Xvfb displays, each containing one real xfce4-terminal, are combined by ffmpeg `hstack` for the video and screenshots. This is a composite of two displays, not two windows on one desktop.
- The shipped adapter archive and first-party codemode, subagents, MCP and web-search bundles are present. The three latter bundles are explicitly enabled on the octet side; Pi's `defaultTools` preference controls codemode activation. The rig gives both sides a `pi` launcher pointing to the same isolated Pi 1.4.0 installation, to avoid a spurious `spawn pi ENOENT` in package child processes. The first S01 recording predates this launcher correction and is retained separately; it is not the canonical run.
- To honor the no-commit instruction, fixture repositories are initialized with an unborn `main` and staged fixture files, rather than creating the harness's normal initial commit. Consequently their Git state includes staged additions and Git-dependent behavior can differ from an ordinary clean, committed checkout. This affects interpretation of git-based tests, including `/simplify`; it is not evidence of a clean-worktree result.
- The dry run exercises S01 startup and one mock prompt on both sides, captures PTY output for diagnostic grep, and records no video. Recorded runs launch directly in real terminals, not through `script` or tmux. Package installation uses `--ignore-scripts` and pinned versions; native prerequisites can remain unavailable. The rig disables pi-lens network installers, passes `--no-context-files` to octet, and uses an isolated model and fixture-specific settings. Timings under a shared two-vCPU Space are indicative, not benchmarks.
- The expected release differences supplied in the handoff remain differences to record; unexpected errors, warnings, missing behavior and visible changes are findings. A successful harness exit is not a parity verdict. Screenshots, videos, manifests, provider request logs and detailed per-setup judgments are retained under `the proof host (not published)`.
