# v0.7.4 bounded startup and context work

This is a local engineering qualification, not a live-provider speed claim or
an end-to-end constant-time claim. Follow the [performance contract](../design/performance.md)
and [benchmark methods](README.md) when extending it.

## Changes and preserved boundaries

- Custom-provider startup registration runs at most four foreground registration
  jobs concurrently. This is not a global thread/discovery bound: existing
  nested discovery threads and detached stale-cache refreshes are unchanged. Each worker still runs the same credential, URL,
  metadata, freshness, discovery, and provider-specific cache code. Catalogs
  merge in registry order, after their work completes; there is no provisional
  model inventory. Offline/manual inventories and single-provider batches do
  not start registration threads. Thread creation failure takes the original
  synchronous path. Built-in discovery and Codex discovery are unchanged.
- Provider-usage reconciliation no longer materializes a vector of references for the whole active
  branch to find a recent measurement. It walks backward to usable usage or
  the nearest local/native compaction boundary, then estimates only trailing
  messages. Without any usage records it returns immediately. No cache or
  durable format was added; model/endpoint affinity, zero-usage rejection,
  branch selection, saturation, and tool/config semantics remain unchanged.

The latter improves a component of resumed-context/status work and capacity
rebuilds, **not material fresh-agent construction**. Structural request
serialization, session replay, layout, and usage-record lookup remain separate
costs. In particular, newer abandoned or wrong-route usage records still make
usage lookup scan the ledger; tests count this separately from entry visits.
This is not total suffix-bounded context estimation.

## Matched local measurements

Apple-silicon macOS, Rust 1.97.1; nine alternating-order trials per cell. Both
implementations are linked into the same test binary: the retained original
algorithm is the control, and the production entry point is the candidate.
Fixture creation and correctness comparisons are outside timed regions.
These are warm process/code measurements with fresh fixture state as specified,
not cold machine/cache measurements. The local machine was not reserved for
benchmarking; report medians, not tail-latency guarantees.

### Startup catalog registration

`custom_catalog_startup_benchmark`, ordinary test profile, v0.7.4. Two loopback
custom inventories each schedule a 100 ms response delay. Cold trials use a
fresh private registry/cache directory. Cached and offline trials reuse only
that trial's completed inventory. No inference is submitted. All 36 expected
inventory requests occurred; both model identities resolve after every case.

| Catalog boundary | Serial median | Candidate median |
| --- | ---: | ---: |
| Cold two-provider registration | 231.15 ms | 118.91 ms |
| Fresh cached registration | 2.37 ms | 2.07 ms |
| Offline cached registration | 1.61 ms | 1.89 ms |

Only the cold case demonstrates the intended removal of serialized discovery
waits. The sub-millisecond cached/offline differences are noisy local costs,
not claimed improvements. This measures the actual startup catalog function,
not process-spawn-to-editable-frame or live service latency. More than four
providers use bounded batches, and a single slow provider remains slow.

The ordinary regression holds the first four of five endpoint responses until
all four requests arrive, and checks that the fifth waits for the next batch.
It also checks distinct synthetic authentication, endpoint URLs, configured
metadata overrides, provider-specific discovered model IDs, offline reuse, an
invalid provider alongside successful jobs, and an unchanged credential registry.
Deadlines guard test progress, not a CI millisecond speed target.

### Provider-usage reconciliation

`provider_usage_suffix_benchmark`, `profiling` profile, v0.7.4. Each trial times
200 calls. Settled histories contain 100, 1,000, or 10,000 entries. The suffix
case appends a measured assistant and one fixed user message. The unmeasured
case contains no usage records.

| History | Serial suffix, median/call | Candidate suffix, median/call |
| ---: | ---: | ---: |
| 100 | 9.61 µs | 0.187 µs |
| 1,000 | 33.30 µs | 0.073 µs |
| 10,000 | 368.68 µs | 0.075 µs |

For no-usage histories, original medians were 12.01, 44.84, and 375.11 µs;
the new empty-ledger check was approximately 1–3 ns/call, near microbenchmark
measurement overhead. Prefer its deterministic zero-entry-visit assertion to
a numerical speedup ratio. The measured-suffix regression performs three entry
visits at increasing history sizes. An adversarial abandoned-record test
explicitly retains and counts the broader usage-ledger scan.

### Actual fresh interactive launch characterization

A separate disposable-home PTY driver launches the v0.7.4 development binary
with `--offline --color never --mouse auto --model custom/probe`, default core
tools, an explicit manual loopback provider, no extensions, and an 80×24 PTY.
After a completed model-labelled frame, it injects a unique draft marker and
waits for a synchronized frame containing it. All nine runs handled Ctrl+D
and exited successfully; no prompt or inference was submitted.

Medians: first completed frame 22.12 ms; model-labelled completed frame
42.33 ms; spawn to frame showing the accepted edit 61.38 ms; injected edit to
completed frame 20.27 ms. These are candidate-only descriptive measurements,
**not a before/after startup improvement**, provider submission readiness, or
terminal-emulator paint. The first frame may be an unbranded startup surface.
The driver continuously drains output during shutdown; an earlier prototype
incorrectly waited without draining the PTY and its failed trials are not
performance evidence.

## Reproduction and verification

```sh
cargo test --offline --locked -p octet-agent --lib
cargo test --offline --locked -p octet-coding-agent --lib app::bootstrap::tests
cargo test --offline --locked -p octet-coding-agent --lib \
  custom_catalog_startup_benchmark -- --ignored --nocapture --test-threads=1
cargo test --profile profiling --offline --locked -p octet-agent --lib \
  provider_usage_suffix_benchmark -- --ignored --nocapture --test-threads=1
```

Observed final results: agent library 498 passed, one manual benchmark ignored;
bootstrap tests 94 passed, one manual benchmark ignored; both explicit
benchmarks completed successfully. An earlier parallel agent-library run had
one unrelated search timeout-fixture failure (`child.pid` missing); its isolated
rerun and the complete final rerun passed. `cargo build --offline --locked -p
octet-coding-agent --bin octet`, Rust 1.86 formatting checks on the owned source,
and `git diff --check` passed. Tests/builds used Rust 1.97, not an MSRV build.

Sanitized raw measurements, the exact measured-source patch, binary/source
identities, and the PTY driver are retained in [v0.7.4-local](v0.7.4-local/README.md).
Host/path identity was removed; numeric samples are unchanged. These are local
engineering measurements, not a public release-binary qualification. Later
qualification-only tests are distinguished from the original timing snapshot.
Earlier interrupted build/benchmark logs and the earlier v0.7.3 development
launch are not the final measurements above.

Unmeasured: live provider latency, extension-enabled launch, loaded cancellation
latency, cross-client comparisons, release-binary editable-frame timing, and
native terminal paint. Existing policy, cancellation, tool-ordering, and
persistence paths were not bypassed to obtain these results.
