# Windows release-candidate qualification, octet 0.8.2

Two unsigned release candidates were built and exercised by a person on native
Windows x64 (non-elevated Windows Terminal PowerShell, unlocked desktop). This
records what was observed, what was verified without a person, and what remains
unqualified. Nothing here is signed or published.

Candidates:

| Candidate | Commit | `octet.exe` | `octet-host.exe` |
| --- | --- | --- | --- |
| RC1 | `30cdec00` | `ad756bc8…` | `5cab7d52…` |
| RC2 | `1fd24c54` | `dcbb5c20…` | `8482956a…` |

Both: Rust 1.88.0, MinGW-w64 GCC 16.1, target `x86_64-pc-windows-gnu`,
`cargo build --release --locked -p octet-coding-agent --bins` (exit 0).
Toolchain note for anyone reproducing: the build needs
`C:\msys64\mingw64\bin` on `PATH` (`dlltool.exe`, `x86_64-w64-mingw32-gcc`).

## Fixed in RC2, verified here

- **Computer use hung on native Windows when octet hosted it.** Driver probes
  inherited the extension's protocol stdin; a Windows child sharing that
  synchronous pipe can stall in C runtime startup. The stall explains the whole
  observed chain: a blank options menu (octet's 5 s `menu/collect` deadline), a
  fallback to a bare command list with an argument prompt, `Check status`
  failing with `-32603`, then a `tool/call` timeout and a closed extension
  process. Every first-party extension subprocess now gets its own stdin.
  The new `HostedStdinTests` pass here, and its control case did not skip: an
  inheriting child genuinely stalls on this machine while a reader thread
  holds a blocking read of stdin.
- **The terminal background query (OSC 11) no longer runs on native Windows.**
  Windows Terminal's reply previously reached the composer as typed text
  (`]11;rgb:0c0c/0c0c/0c0c\`). Automatic light/dark detection is off on native
  Windows; `OCTET_COLOR_SCHEME` and the theme picker still choose explicitly.
  *Not yet re-observed by a person on RC2* — see "Still open".
- **The queued-message hint names Alt+Q on Windows and WSL**, the chord that
  key set actually binds, instead of Alt+Up. Verified by a person: the hint
  reads Alt+Q and Alt+Q restores the queued message.

## Verified without a person

- Extension suites on a pristine Linux clone, mirroring the CI `ubuntu`
  first-party lane: SDK 130, browse 122, computer-use 335, mcp 102,
  subagents 109, web-search 54 — all passing, no skips beyond the documented
  live-driver ones.
- Native Windows suites: SDK 130 passing; computer-use 335 with one
  environmental error (`WinError 1314`, this account cannot create the symlink
  a cursor-theme test needs; CI's elevated runner can); subagents 110 with a
  failure set byte-identical to RC1, so the launcher stdin change introduced no
  regression. The browse, mcp, subagents and web-search suites also have
  pre-existing Windows-only failures (symlink privileges, `cp1252` console
  decoding, absent herdr/tmux, file locking) that CI gates on Linux only.
- `scripts/tests/test_extension_subprocess_stdin.py`: 2 passing.
- TUI unit tests: keymap 35, input overlays 3, queueing 14, all passing.
- `windows_conpty` against the packaged binary: 3 scenarios pass when they run.
- Release tooling: all five extension bundles packaged twice and compared
  byte-identical, with `version = 0.8.2` and `requires_octet = "=0.8.2"`
  verified inside every archive.
- Binary smoke: `--version` reports `octet 0.8.2`, `--help` succeeds, the
  `octet-host` hello handshake returns a valid frame, and both start with only
  the Windows system directories on `PATH`.
- **Live extension driver use on Windows: the MCP extension drove Ableton
  successfully.** This is the first live Windows extension-driver result; CI
  only proves the no-driver fail-closed path.

## Still open

- **A multi-line paste submits once per line in Windows Terminal.** Console
  input arrives as bare records with no paste markers, so octet cannot
  distinguish a paste from fast typing. Documented in `docs/windows.md`; no fix
  is planned for 0.8.2. Use `@file` references for long text.
- **Cursor flicker while streaming.** Every frame toggles the console cursor
  visibility and repositions it, which is visible as a ghosting block cursor
  during streaming in Windows Terminal. The tester attributes this to Windows
  Terminal's cursor handling and accepts it; it is not fixed in 0.8.2.
- **The ConPTY first-run scenarios do not complete on a developer machine.**
  They need a profile with no configured provider, self-skip when one exists,
  and with a clean profile they time out waiting for the composer after
  "Continue without". This reproduces identically on `30cdec00` and `1fd24c54`,
  so it is not a regression from RC2, and it is unresolved: either first-run
  setup drifted from what the harness expects, or the inbox conhost differs
  from the CI runner. Until that is settled these scenarios validate nothing
  on a workstation, which includes the OSC 11 regression assertion.
- **The models.dev snapshot is stale** relative to the live service.
  Regeneration changes OpenRouter DeepSeek v4 pricing, capability records and
  the receipt. The release gate stays red until the snapshot is regenerated
  and the price changes are reviewed.
- **The interactive startup composer was not re-observed by a person on RC2.**
  The fix is structural (the query is not sent at all on Windows), but the
  manual confirmation is still outstanding.

## Method note

Provider-free ConPTY runs require hiding the account's octet credentials. This
was done and recovered byte-identically, but it is not a procedure to repeat:
a child process re-created the directory mid-run and nested the restore. Use a
disposable `USERPROFILE` or home directory for provider-free scenarios instead.
