# octet 0.10.0

**Local release candidate — unreleased source candidate, not a published release.**
Public 0.10.0 artifacts do not exist and final qualification is incomplete.
The last published native downloads remain on the
[v0.9.6 release page](https://github.com/skaft-software/octet/releases/tag/v0.9.6).
This working tree is a dirty integration overlay, not an immutable release SHA.
Diagnostic source archives must retain their overlay identity; clean-tree
packaging gates remain mandatory before exact-source artifacts can be qualified.

## Added

- **Pi in the local candidate catalog.** The single extension catalog now selects
  `octet-pi-compat` alongside codemode, computer use, MCP, subagents and web search.
  Six candidate manifests use distribution version 0.10.0, exact host requirement
  `=0.10.0` and unchanged API `0.4`. Catalog inclusion is delivery preparation,
  not evidence that the six final archives have been built or accepted.
- **Explicit local activation guidance.** Use this checkout's built host and
  reviewed source, or an explicit local archive such as
  `/absolute/local-candidate/octet-pi-compat-0.10.0.tar.gz`; do not request a
  nonexistent public 0.10.0 asset. Native/npm packages do not embed optional
  executable bundles. Installation and discovery remain inert.

## Fixed

These fixes have focused source/fixture evidence in the integration work;
rebuilt original-setup guest and final-artifact acceptance remain separate gates.

- **Composed editor/footer theme changes:** an applied theme preference write is
  acknowledged by its exact persistence receipt, avoiding a redundant resource
  reload that retired live Pi mounts. Independent resource edits still reload.
  Native TOML appearance remains independently available.
- **Startup tool registration:** a Pi startup callback can await its late-tool
  catalog acknowledgement without waiting behind its own lifecycle lock.
  Generation, reload, validation and failed-acknowledgement fences remain intact.
- **Command context:** `ctx.getSystemPrompt()` reads the actual native system
  prompt through a live, admitted command request, rather than requiring a
  missing cached snapshot. Retained/headless prompt reads are not newly qualified.
- **Headless model facts:** App-deferred startup receives credential-filtered
  model/scoped facts, including refreshed mirrored defaults. Immediate starts
  before App construction and initialize-time facts remain outside this repair;
  unavailable facts are still refused, not invented.
- **Legacy undo input:** raw terminal byte `0x1f` is decoded as Ctrl+- to match
  Pi 1.0.2, while preserving its raw spelling for listeners. Explicit Kitty
  Ctrl+7 remains distinct; a legacy Ctrl+7 binding relying on that ambiguous byte
  changes meaning. Rebuilt original-editor replay remains required.
- **Windows managed updates:** validated replacement uses locked recovery rather
  than unavailable atomic directory exchange. Failure restores the old bundle,
  or retains a backup with recovery instructions; listing/global managed
  discovery recover interrupted updates. Linux/macOS keep atomic exchange.
  Focused local and separate upstream GNU Windows evidence do not qualify the
  combined candidate's MSVC artifacts or attended Windows use.

## Changed

- Workspace/native identity, exact internal pins and workspace lock entries,
  independent codemode package/lock, Python/TypeScript source SDK metadata and
  checked-in installer identity target 0.10.0. The Rust SDK stays independently
  0.8.2; Pi stays pinned to 1.0.2; the adapter's private npm package stays 0.1.0.
  API/schema/example versions and historical evidence are unchanged.
- **Enabling the stock Pi bridge is executable consent:** it automatically
  mirrors this machine's enabled Pi setup and runs its factories/imports with
  OS permissions. It is not a sandbox. Native provider-credential disclosure
  still needs a separate reviewed opt-in; no credential access is silently
  authorized by catalog inclusion, installation or enablement.
- Pi requires Node >=22.19.0 and entrypoints reject older Node before loading
  dependencies/factories. Actual older-runtime and packaged-bundle negatives
  remain unqualified; Bun remains unqualified. Python-script adapters need
  Python >=3.11 with `venv`/`ensurepip` or explicit private-runtime setup, not a
  mandatory Python probe for every native launch. Codemode needs neither Node
  nor Python at runtime.

## Known limitations

- **No blanket Pi parity.** The [27-row API ledger](../pi-extension-api.md)
  retains partial session/context/UI/provider/process/MCP contracts. Factory
  loading, synthetic hosts, historical receipts and catalog membership do not
  establish installed-Pi task acceptance or model quality.
- **Guest and visual acceptance remain open.** Fresh rebuilt candidate journeys
  across the supported setup/platform matrix, including original composed
  editor/footer theme changes, context commands, headless tools, raw-byte undo,
  disable/reload and restart, need artifact-bound screenshots/recordings and
  independent lifecycle/tool effects. Earlier binaries do not qualify new source.
- **Final delivery remains open.** A separately authorized coherent Git freeze,
  exact-source workspace/quality/adapter/editor-native gates, six complete local
  extension archives with checksums/source identity, matching native archives,
  integrity/extraction checks and isolated archive installation/activation are
  still required. Dirty-source diagnostics are not exact-HEAD packages.
- **Windows remains preview and unqualified for this combined candidate.** GNU
  tests do not establish MSVC/native artifact, multiline paste, physical-console,
  desktop-driver or provider acceptance.
- **No live/model-quality acceptance.** No final-candidate live provider,
  credential/signing, billing, model-quality or whole-release performance claim
  follows from these changes. Existing narrow benchmark boundaries remain.
- **Nothing is published by this preparation.** Signing, public installation,
  GitHub release/tag/workflow actions, npm platform-first provenance checks,
  Homebrew and SDK registries need their own authorization and evidence.
